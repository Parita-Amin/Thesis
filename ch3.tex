\section{Describing New OWL Vocabularies}
\label{sec:describenewowlvocab}

There are editors available that help the publishers to create their own \acp{lov}.
Clunis~\cite{clunis2019comparative} compared several editors, based on the following criteria: 
\emph{General Description} 
(developers' details, and accessibility on the internet), 
\emph{Software Architecture and Tools Evaluation} 
(semantic web architecture, support for plug-ins, backup management, and ontology storage), 
\emph{Interoperability} 
(interoperability with other ontology tools, support and translation for other languages) 
\emph{Knowledge Representation} 
(Knowledge Representation paradigm of knowledge model, axiom language, and methodological support), 
\emph{Inference Services} 
(built-in inference engine, other attached inference engines, and constraint/consistency checking), and
\emph{Usability} 
(graphical taxonomy, graphical views, zooms, collaborative working, and ontology libraries).

Considering that study and the popularity amongst researchers, 
Protégé has been used for the development of the instrument 
to support this research and thesis work.

\subsubsection{Usability of Protégé}
\label{subsubsec:usabilityofprotege}

The \ac{iso} standard 9241\footnote{\tt https://www.iso.org/standard/63500.html} 
defines usability as 
``the extent to which a product can be used by specified users 
to achieve specified goals with effectiveness, efficiency, 
and satisfaction in a specified context of use''. 
In usability engineering, 
Jacob Neilson~\cite{neilson1994usability} 
suggested five qualities of a usable product: 
{\tt learnability}, {\tt efficiency}, {\tt memorability}, 
{\tt errors} (low rate, easy to recover), and {\tt satisfaction}. 
These were the original five dimensions of usability 
which were then re-termed using words starting with the letter
``E'' by Quesenbery~\cite{quesenbery2003dimensions}, 
and they became popular as the five E's of usability. 
The new terms are 
{\em Effective}, 
{\em Efficient}, 
{\em Engaging}, 
{\em Error-tolerant}, and 
{\em Easy-to-learn}.

The five dimensions of usability can be considered 
while designing as well as for evaluation. 
While designing, 
the engineers consider the five dimensions as goals to be achieved 
whereas while testing and evaluation, 
they are considered as the requirements necessary for the designed model. 
The five dimensions of usability were used to assess the usability of Protégé and 
the report of the evaluation is as follows:

\emph{Effective}: The task is completed accurately

Protégé is an effective design as it allows the users to build ontologies and 
use other tools precisely. 
The users can complete the desired tasks accurately 
using the set of facilities available.

\emph{Efficient}: The task is completed quickly

It is easy and straightforward to describe the vocabularies and build ontologies. 
All the desired tasks in Protégé can be completed quickly 
(without wasting much time) 
as it is easy to look for the facilities using the menus and tools available. 
Hence, 
Protégé is an efficient ontology builder.

\emph{Engaging}: The look and feel of the design is interactive and engaging 

The tools and menus in Protégé are interactive 
which leads to a better experience for the user. 
Also, 
the layout and the components are attractive and 
decent for the user to use this ontology builder 
whenever necessary. 
Overall, 
Protégé gives an engaging and satisfactory user experience.

\emph{Error-tolerant}: Error prevention and data recovery in case any error is committed

Protégé provides options for modifications, additions, 
and deletions of classes, objects, and properties, 
which allow the users to correct the errors that were committed. 
Also, 
the deleted classes can be recovered using {\tt Undo} 
from the edit menu resulting in proving Protégé as an error-tolerant design.

\emph{Easy-to-learn}: The interface should be easy to learn

Protégé is easy to learn as it has a familiar look and 
commonly used names for the tools and menus making it easy 
for the users to adapt and know them nicely. 
Also, 
the help documentation
along with a list of some frequently asked questions is available,
which helps the users in the correct direction whenever they are lost.

\subsection{Procedure to Describe OWL Vocabularies Using Protégé}
\label{subsec:protegeprocedure}

This Section focuses on a step-wise methodology 
that has been followed to create new \ac{owl} 
vocabularies using Protégé,
which
is available for use as a web application or
for download in the case of the desktop application.

To commence with the process of building an ontology, 
a new project needs to be created 
with a unique \ac{iri}\footnote{\tt https://www.w3.org/2011/rdf-wg/wiki/IRIs/RDFConceptsProposal} 
and the ontology version. 

\subsubsection{Classes and Class Hierarchy}
\label{subsubsec:classhierarchy}

The next step is to create classes and build the hierarchy for the class nodes. 
Each entity in Protégé is directly or indirectly a child node of the {\tt Thing} class. 
Also, 
each object has a name-value pair, 
which generally are the nodes of the {\tt Domain\_Entity} class, 
an inherited class of Thing. 
Initially, 
four classes, 
{\tt Thing}, 
{\tt Independent\_Entity},
{\tt Domain\_Entity}, 
and 
{\tt Value} 
are created using class hierarchy, 
as shown in Figure~\ref{class-hierarchy}. 

\begin{figure}[htp]
    \centering
    \includegraphics[width=15cm]{images/ch3/protege/class-hierarchy.png}
    \caption{Class Hierarchy of Thing, Domain\_Entity, Independent\_Entity, and Value}
    \label{class-hierarchy}
\end{figure}

To create a class hierarchy for the classes that represent entities in an ontology, 
there are three steps to be followed:

\begin{enumerate}

    \item Select {\tt owl:Thing} in the Class Hierarchy View 
    of the Classes tab from the Windows menu followed by selecting {\tt Create class hierarchy...} 
    from the Tools menu, 
    to open a {\tt Enter hierarchy} pop-up window 
    which allows the users to add classes to the ontology.
     
    \item Enter the class names in the pop-up window starting from the left. 
    For the child nodes, 
    leave some spaces before writing the class name. 
    Each horizontal line consists of one class name, 
    as shown in Figure~\ref{enter-hierarchy-pop-up}. 
    
    \begin{figure}[htp]
        \centering
        \includegraphics[width=15cm]{images/ch3/protege/enter-hierarchy-pop-up.png}
        \caption{Enter hierarchy Pop-up Window} 
        \label{enter-hierarchy-pop-up}
    \end{figure}
    
    \item On clicking {\tt Continue} 
    on the pop-up window in Figure~\ref{enter-hierarchy-pop-up}, 
    it opens up a new pop-up window.
    Here, 
    it is important to state whether one wants the sibling classes to be disjoint or not. 
    The checkbox needs to be checked accordingly. 
    Usually, 
    it is recommended to create disjoint sibling classes which can be changed later as necessary.
    
\end{enumerate}

Once the classes are added, 
the next step is to describe the classes. 
Descriptions of classes like 
{\tt Equivalent to}, 
{\tt SubClass Of}, 
{\tt Instances}, 
{\tt Disjoint With} and so on 
can be added using the Description view of the Class tab 
(shown in Figure~\ref{class-hierarchy}). 
Each class can be described individually by selecting a particular class and 
adding details to the description view. 

\subsubsection{Object Properties and Object Property Hierarchy}
\label{subsubsec:objectproperties}

The next step in building the ontology, 
after describing the classes, 
is describing the {\tt Object Properties}. 
Object properties are used to link the entities (classes in Protégé). 
The {\tt owl:topObjectProperty} 
is the root node of the object properties' hierarchy. 
The hierarchy for object properties can be built 
by selecting a property in the Object Property Hierarchy view 
of the Object Property Views tab and 
then going to the tools menu and selecting {\tt Create object property hierarchy...}. 
The remaining steps are similar to the ones that are followed for building class hierarchy 
(Section~\ref{subsubsec:classhierarchy}).    
Also, 
the description view of object properties hierarchy 
allows the user to describe the object properties. 
The details that can be added or modified using the description view are 
{\tt Equivalent To}, 
{\tt SubProperty Of}, 
{\tt Inverse Of}, 
{\tt Domains (intersection)}, 
{\tt Ranges (intersection)}, 
{\tt Disjoint With}, and 
{\tt SuperProperty Of (Chain)}. 

The names of the object properties usually start with an {\tt is} or a {\tt has}. 
For instance, 
consider two classes from the pizza ontology: 
{\tt Pizza} (class 1) and {\tt PizzaBase} (class 2). 
To describe the link between class 1 ({\tt Pizza}) and class 2 ({\tt PizzaBase}) 
such that class 1 has value class 2 and class 2 is value of class 1, 
the properties {\tt hasBase} and {\tt isBaseOf} would be used respectively, 
as shown in Figure~\ref{object-properties-for-pizza-and-pizzabase}. 

\begin{figure}[htp]
    \centering
    \includegraphics[width=15cm]{images/ch3/protege/object-properties-for-pizza-and-pizzabase.png}
    \caption{Object Properties for Classes {\tt Pizza} and {\tt PizzaBase}}
    \label{object-properties-for-pizza-and-pizzabase}
\end{figure}

Each object property might have a corresponding inverse property. 
For the above instance, 
it can be said that:

\begin{center}
    \par Pizza hasBase PizzaBase \textbf{is equivalent to} PizzaBase isBaseOf Pizza
\end{center}
\noindent
Here, 
{\tt hasBase} is inverse of {\tt isBaseOf} 
and {\tt isBaseOf} is inverse of {\tt hasBase}. 
Apart from inverse, 
domain and range\footnote{\tt http://protegeproject.github.io/protege/views/object-property-description/} 
are two other important parts of description of object properties. 
According to Horridge et al.~\cite{horridge2011practical}, 
in \ac{owl}, 
``domain and range are not constraints to be checked. 
They are axioms which are used by the reasoner to make inferences''. 
As shown in Figure~\ref{domain-and-range-for-hasBase-and-isBaseOf}, 
{\tt Pizza} acts as the {\tt domain} and 
{\tt PizzaBase} acts as the {\tt range} 
for {\tt hasBase} whereas 
for {\tt isBaseOf}, 
{\tt PizzaBase} is the {\tt domain} and 
{\tt Pizza} is the {\tt range}. 

\begin{figure}[htp]
    \centering
    \includegraphics[width=12cm]{images/ch3/protege/domain-and-range-for-hasBase-and-isBaseOf.png}
    \caption{Domain and Range Classes for {\tt hasBase} and {\tt isBaseOf}}
    \label{domain-and-range-for-hasBase-and-isBaseOf}
\end{figure}

\subsubsection{Data Properties and Data Property Hierarchy}
\label{subsubsec:dataproperties}

Furthermore, 
the {\tt Data Properties} 
can also be described for ontology.
``An ontology data property provides a relation 
to attach an entity instance to some literal datatype value 
(an \ac{rdf} number, string or data for example) 
that is a measure or estimate of 
what that data property is about.''\footnote{\tt https://ddooley.github.io/docs/data-properties/}

In Protégé, 
the {\tt owl:topDataProperty} 
is the root node of the data properties' hierarchy. 
The data property hierarchy can be built by selecting a property 
in the Data Property Hierarchy view of the Data Property Views tab and 
then going to the tools menu and 
selecting {\tt Create data property hierarchy...}.  
The remaining steps are similar to the ones that are followed 
for building class and object property hierarchy 
(Section~\ref{subsubsec:classhierarchy}). 
Data properties can be described using the description view 
of data properties of hierarchy which included details like 
{\tt Equivalent To}, 
{\tt SubProperty Of}, 
{\tt Domains (intersection)}, 
{\tt Ranges}, and 
{\tt Disjoint With}.

\subsubsection{The FAIR Principles}
\label{subsubsec:fairprinciples}

After developing the linked data vocabulary, 
the next step is to use this vocabulary, 
either to develop another ontology or to map data but
before that, 
it is important to check 
if the developed vocabulary makes use of best practices.
The FAIR principles~\cite{fair2016principles} 
were published in 2016 with the intention of improving the {\em Findability},
{\em Accessibility}, {\em Interoperability}, and 
{\em Reuse} of digital assets. 
The FAIR principles can be found online\footnote{\tt https://www.go-fair.org/fair-principles/}. They are:

\begin{itemize}
   
    \item Findable: 
    The metadata and data should be easy to find for both humans and computers in order to be reused.
   
    \item Accessible: 
    After finding the data,
    the data needs to be accessible, possibly including authentication and authorization.
   
    \item Interoperable: 
    Users should be able to integrate the data with other data, and 
    interoperate with applications or workflows 
    for analysis, storage, and processing.
   
    \item Reusable: 
    To optimize the reuse of the data, 
    metadata and data should be well-described 
    so that they can be replicated and/or combined in different settings.

\end{itemize}

Chapter~\ref{chap:proofOfConcept} discusses the results of using 
FAIR principles to evaluate the {\tt Survey} vocabulary.

\subsection{Data Validation}
\label{subsec:datavalidation}

Hepting collects feedback responses and 
manually stores them in spreadsheets. 
Much of this data is collected on paper,
with a handful of spreadsheets created directly
from within the University of Regina's learning management system.
It is important to validate the stored data 
so that the data only consists of acceptable values. 
According to Ekaputra and Xiashuo~\cite{shacl4protege}, 
``One of the challenges of adopting \ac{swt} 
for enterprise data integration is to provide the means 
to define and validate structural constraints over \ac{rdf} graphs.'' 
To address this challenge, 
they developed SHACL4P, 
a Protégé plugin. 
SHACL4P is used for defining and validating \ac{shacl}, 
which is a W3C standard 
for the validation of contents of 
an \ac{rdf}-style graph database\footnote{\tt https://www.w3.org/TR/shacl/}. 
\ac{shacl} uses {\tt shapes} to describe constraints.

\subsection{Licensing Linked Data}
\label{subsec:licensinglinkeddata}

\ac{w3c}~\cite{hyland2014bestpractices,DWBP2017tr,DWBP2019impl} 
advises that it is critical to identify the owner of any data published on the web 
and to explicitly link the licence to the data itself. 
It is simpler to attach a licence that goes with the data itself 
when publishing linked open data. 
When data has a clear, 
agreeable licence attached to it, 
people are more likely to reuse it.

The Creative Commons\footnote{\tt https://creativecommons.org/} 
website is a useful resource for open data providers. 
The legal and technical framework for publishing digital content is 
developed, supported, and maintained by Creative Commons. 
There are different licenses available like  
{\tt Attribution-ShareAlike 4.0 International}\footnote{\tt https://creativecommons.org/licenses/by-sa/4.0/}

\subsection{Publishing Linked Open Data}
\label{subsec:publishinglod}

According to Petrou et al.~\cite{irene2014publishlod}, 
the linked data principles state that dereferencable \ac{uri}s 
are the preferred method of accessing linked data and that the data should be openly available. 
When accessed, 
these \ac{uri}s offer accurate descriptions of the concepts they stand for in a number of formats. 
\ac{rdf} dumps and \ac{sparql} endpoints are hence 
two ways that users can access the data. 
Dereferencing of the data is accomplished using the specialised \ac{rdf} store, 
and all the data are accessible via a \ac{sparql} endpoint service 
or through the faceted browsing feature, 
which allows users to search resources and move between them.
